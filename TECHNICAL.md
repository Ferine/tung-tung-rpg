# How it is built

The hardware side of TUNG TUNG SAHUR: what sits in which layer, what the eight
bugs were, and how the art and the orchestra get made. `README.md` is about the
game.

Everything on screen is generated by the Python in this directory — no art
program, no tracker. `gen_assets.py` is the whole pipeline. Which is fitting,
because so is everybody in it.

The music is the one thing not made from nothing, and deliberately: the
instruments are real recordings, because that is what a 16-bit RPG score is.
FF6 and Chrono Trigger are not synthesised — they are an orchestra cut into a
few hundred bytes per instrument and played back through the SPC700. Same
process here, on CC0 material. `SAMPLES.md` has the details and the licence.

## Layers

BG mode 1. The priority order for the 3-screen modes (development manual
Appendix A-19) reads, rear to front:

```
back  BG4.0  BG3.0  OBJ.0  BG4.1  BG3.1  OBJ.1  BG2.0  BG1.0  OBJ.2
      BG2.1  BG1.1  OBJ.3      [BG3.1 jumps frontmost when $2105 D3 = 1]
```

Windows have to cover the party sprites the way FF's do, and the only band
that sits above an OBJ without also demanding BG3's four colours is BG2.1 —
directly in front of OBJ.2. So:

| layer | contents | note |
|---|---|---|
| BG1 | region map / battle backdrop | every tile priority 0; a rendered region uses BG palettes 0-2 and 4-7, a backdrop 2 and 4-7 |
| BG2 | text and windows | every tile priority 1 |
| BG3 | unused | its palette would overlap BG1's (A-17) |
| OBJ | characters | priority 2, under the windows |

## VRAM

Word addresses. Character bases are 4K-word granular ($210B/$210C) and tilemap
bases 1K-word granular ($2107–$210A), which is what the gaps are.

```
$0000-$0FFF  OBJ characters 000-0FF   resident: hero, five battlers
$1000-$1BFF  OBJ characters 100-1BF   scratch: this fight's enemies
$1C00-$1FFF  OBJ characters 1C0-1FF   scratch: the speaking portrait
$2000-$2FFF  font + window tiles           BG2 character base
$3000-$3FFF  region tileset                BG1 character base, field
$4000-$4FFF  region tilemap 64x64          BG1 tilemap base
             (the title borrows $3000-$4FFF: 512 characters)
$5000-$53FF  text tilemap 32x32            BG2 tilemap base
$5400-$57FF  battle tilemap 32x32          BG1 tilemap base, battle
$6000-$6FFF  battle backdrop tileset       BG1 character base, battle
```

Twenty-four enemy designs come to 21KB. The second OBJ page is therefore a
scratch window: a fight uploads exactly the designs it needs, behind the
encounter wipe, in forced blank.

The portrait shares that page without ever colliding with it. A 32x32 OBJ at
name 448 spans character rows 12-15; a 64x64 boss at name 256 covers rows 0-7,
and six small enemies cover rows 0-1. Nothing reaches row 12.

## Raster

Two H-DMA channels. The eight DMA channels are shared between general-purpose
and H-DMA and the manual is explicit that one channel must not do both
($420B); channel 0 is every pvsneslib GP-DMA and channel 7 is the OAM copy the
library's NMI issues, so the raster takes 1 and 2.

- **ch1 → $2132 COLDATA**, one byte a line. Colour math is left on in subtract
  mode permanently and the table decides how much lands on each line, so the
  palette holds the brightest version of the sky and the raster darkens it
  toward the top. That buys a gradient far smoother than four dithered bands,
  and a vignette for free.
- **ch2 → $210D BG1HOFS**, two bytes a line (write-twice). Eight phase tables
  in ROM; the game advances which one the channel reads, so water ripples for
  three stores a frame instead of rebuilding 450 bytes.

## Mode 7 encounter warp

Field-to-battle transitions briefly become their own full-screen Mode 7 state.
The generated 128x128-character night field occupies the low-byte plane of
VRAM words `$0000-$3FFF`; its 8bpp characters occupy the corresponding high
bytes, exactly as Appendix A-11/A-15 prescribe. A single affine matrix rotates
the field while its scale falls from `$0600` to `$0080`, making the concentric
wake-rings rush toward the camera. The existing BG1 mosaic then closes over the
last part of the fade.

That fixed Mode 7 layout overlaps the normal OBJ, font and field-character
windows. The warp therefore loads under forced blank and is deliberately
disposable: before enemy art is streamed, the engine restores the resident
sprite sheet, font, current region characters, their palettes, Mode 1 and the
normal BG enables. The field map and both UI/battle maps sit above `$3FFF`, so
they survive the effect and the battle-return path still needs no region load.

## Eight bugs worth writing down

**A 64x64 OBJ wraps inside its character page.** A-4 says a large OBJ's cells
are "taken row-wise from the 16x16-character page" — a page of 16 by 16
characters, and the index wraps *inside it*. The boss sat at name $E0, row 14,
so its bottom six rows wrapped back to rows 0–5 and it drew its own wingtip on
top of six copies of the walking sprite. VRAM, OAM and $2101 were all correct.
`gen_sprites.py` now asserts a large sprite's block fits its page both ways.

**VRAM is writable in forced blank or V-blank only.** The enemy art upload ran
from the field update, in the middle of a visible frame. It wrote nothing at
all, silently, and every enemy in the game was invisible with a perfectly
correct OAM entry pointing at an empty page.

**WRAM is not zeroed at reset.** pvsneslib's crt0 clears the direct page and
the stack, not the whole of bank $7E. `menuActive` came up 64 on a cold boot,
which made `main()` skip `fieldDraw` — so the hero was invisible for a whole
session with his OAM entry sitting there, parked and correct.

**A 64x64 tilemap is not one 64-wide array.** SC size 3 is four 32x32 screens
stored consecutively — SC0 SC1 / SC2 SC3, each with a 32-entry row stride
(A-14). Written row-major across all 64 columns instead, the PPU reads screen
row *r* from map row *r/2* and the world comes out interleaved.

**Glyph 0 is a space and a space is transparent.** Right over the field, wrong
inside a window: every gap in `TUNG  130  12` punched a hole in the fill and
the status box came out striped with the backdrop. Same bug twice — once in
`textPutPal`, once in the message box's own typing path.

**Battle borrows two BG palettes and the field never got them back.** Slots 0
and 1 hold red and green glyphs for the duration of a fight; nothing restored
the region's own colours on the way out, so the world came back from every
battle in lavender and orange and stayed that way for the session. The field
menu has the same problem in reverse and additionally needs BG1 *off*, because
a glyph's background is transparent and every letter was showing the recoloured
map through itself.

**WRAM is not zeroed at reset — and file statics count.** The fix for that had
been `globalsInit`, which zeroes the globals in `globals.c`. `msgFaceForced` is
a static inside `text.c`, so it was never in that list; the first line of the
first conversation after a CONTINUE read whatever was in the byte at power-on
and asked for portrait 222. It only reproduced on a loaded save, because a new
game plays the opening scene first and that consumed the garbage.

**A full repaint of the battle screen costs eight frames.** Clearing 1024 text
cells and redrawing every window frame, every frame, was ~1400 tile writes plus
the clear, and the 65816 got through it roughly once every eight frames. The
ATB crawled and — worse — a one-frame `padsDown` pulse was missed seven times
out of eight, so the command window looked frozen and the battle unwinnable.
Draw the layout when the layout changes, and only the volatile cells otherwise.

## Portraits

Eight busts — Tung, La Nonna, the four guardians who join, Il Silenzio and the
Ballerina — in a six-tile frame stacked directly on top of the message box.

Three details make it cheap:

**One OBJ, not four.** `ppuSetFieldMode` selects `OBJ_SIZE16_L32`, so in the
field a *large* OBJ is 32x32 — a portrait is one OAM slot. (Battle uses
`OBJ_SIZE32_L64`, which is why the portrait is parked on the way in: the size
pair changes underneath anything still on screen, and a bust left showing would
come back as a 64x64 read of whatever follows it in VRAM.)

**Priority 3.** The frame is BG2 at tile priority 1, and A-19 puts BG2.1 in
front of OBJ.2 — the priority everything else in the game uses. A portrait
drawn there is behind its own frame. OBJ.3 is the only band in front of it.

**Four transfers, one a frame.** 512 bytes will not fit in a V-blank next to
the OAM copy the NMI already issued and the text-layer DMA behind it. A 32x32
OBJ's character rows sit 16 names apart (A-4), so the art is four runs of 128
bytes anyway — one per frame, skipping the frames the tile animation wants,
and the OBJ is not shown until all four have landed. The box types its text in
over rather longer than four frames, so the wait is invisible.

### Who is talking

Nothing had to be annotated. The script was already written as

```c
"LA NONNA: \"Tung. TUNG. I know. Three nights you bang that thing.\""
"\"Something came up the east road and took the WAKING out of people.\""
```

— a name and a colon when somebody starts speaking, a bare opening quote when
they carry on. So the portrait is chosen by matching that prefix, and a line
that opens with a quote keeps whoever spoke last. Narration matches neither and
gets no portrait, which is right for the two thirds of the script that is
narration. Checked across the whole script: no scene opens on a quote and no
narration line does either, so the two cases never collide.

`sceneFace()` covers the handful of beats where the camera is on somebody the
narrator is talking *about* rather than *as* — the opening, where Tung beats
the first call, and the ending.

`python3 preview.py portraits` renders all eight.

## The sleepwalkers

Twenty-two wandering NPCs across the seven regions, in `src/npc.c`, on the same
cell-based step the hero uses: a 16-dot cell, eight frames of two dots, so one
is only ever *at* a cell or between two of them and everything that needs to
know where one is can ask in cell units.

**A walker owns two cells for the length of a step** — the one it left and the
one it is entering. Owning only the destination lets the player walk into the
cell being vacated and end up standing inside somebody; owning only the origin
has the same result one step later. `npcAt()` answers for both, and `fieldUpdate`
consults it before committing the hero to a step.

**Their own random generator, not `rand()`.** The encounter counter is armed off
`rand()`, so a shared sequence would make the pacing of random battles depend on
how many sleepwalkers happened to be deciding something on a given frame. Six
lines of LCG is cheaper than that coupling.

**Three poses, not four.** Down, up and side, two frames each — the side pose is
drawn facing right and the OBJ engine mirrors it for the other direction, which
is what `oamSet`'s H-flip argument is for. Two characters saved per design on a
page that had sixty-four left in it: the party's battle sprites are 32x32 and
had taken 192 of the 256.

They draw into OAM entries 1 upward, the hero keeps entry 0, and the dialogue
portrait keeps entry 16 (`FACE_OAM`). Off-screen walkers are skipped: a region
is 512 dots across against a 256-dot window, so most of them are outside it at
any time, and an OBJ parked off screen still costs a slot against the
32-per-line limit.

`gen_world.py` picks the home cells, and rejects any cell whose four neighbours
include an event: a sleepwalker parked on a door is one standing between the
player and the shop, and one parked on an exit is worse.

One thing the generator now catches that it did not before: `place()` tracks
which characters of the resident page are spoken for, so two sprites at
overlapping names fail the asset build instead of interleaving their pixels and
coming out wrong on screen.

## Field sprites

Pre-rendered too (`render_field.py`): the hero's eight walking poses and the
sleepwalkers' fourteen, the same figures and lights as the battlers, cut to the
field's 16x16 OBJ. They were the last hand-drawn sprites, and the ones on
screen longest.

The camera looks down at 0.45 radians instead of the battlers' 0.2, because
the field is drawn in three-quarter view, roofs and house fronts at once. The
tilt shows the top of the drum, which is what makes it read as a log. It also moves faces: anything on the front of a head
lands lower on screen than its height says, so eyes sit higher than they
would face on — placed where the model says, the sleepwalkers' shut eyes
landed on the chin line in the outline colour and disappeared.

One unit is eight dots here, and a detail thinner than a dot loses the
downsample's majority vote and is not drawn at all. Tung's brows have to slope
a whole dot across their length or they merge into a headband, and shut eyes
are painted onto the head as a band a dot tall instead of modelled.

Frame 0 is also the standing pose, for the hero and for a sleepwalker at rest.
From the front and back the two frames are mirror images — one foot a dot
higher, then the other — so standing reads as weight on one foot rather than
frozen mid-stride. In profile frame 0 has the feet together.

The bat changes hands. On the shoulder it is in the silhouette from the front
and behind, but in profile the near shoulder puts it across his face, so in the
side views it is slung across his back from the far hand. The hero's left is
therefore its own render rather than his right mirrored — which the OBJ engine
could do, and does for the sleepwalkers.

`gen_sprites.field_poses()` is the single list of keys, palettes and sheet
names; the bake renders from it and the sheet is placed from it. The painters
stay as the fallback for any kind `FIELD` does not cover.

## The title screen

Pre-rendered (`render_title.py`): a hillside village under the moon, and the
logo as bevelled gold — `gen_title.py`'s own letterforms, given height by a
distance transform inside each letter and lit through the resulting normals.
It is a relief, not a raymarch, which is what a logo on a title screen is.

A shaded logo is mostly unique characters, and the screen comes to 367 — more
than the 256 the battle window holds. On the title nothing uses the field's
window, so BG1 points at `$3000` and gets everything up to the text map at
`$5000`: 512 characters. Every way off the title queues a region, and
`fieldLoadArea` writes the field's characters and map back over it.

Two things still move, and neither touches a tile — but the mechanism changed.
The painted title rotated four CGRAM entries through horizontal bands of a flat
logo. A shaded logo has no bands, and rotating its ramp would scramble the
shading. So the title is rendered eight times, with a light circling the
letters and the stars at different strengths, and the eight pictures are cut
*together* as one 24-channel image: one set of characters, eight sets of
palettes. The animation is a 160-byte palette upload every five frames.

The title also has its own sky table now. It used to inherit whichever
region's H-DMA was programmed last, and a battle sky's subtract turned the gold
to mud by the second line of letters.

## The land

Every region is pre-rendered too: `render_land.py` is the engine and
`render_regions.py` says what each character is in each place — the
moonlight, the materials, a well or a spring or a tank. `terrain.py`'s painters
stay as the fallback for a region with no look, and a painted region stands
still.

A battle backdrop is one picture. A region is 1024 cells drawn from sixty-odd
metatiles, and every one of them has to meet every neighbour it is ever put
beside. Four things make that work.

**The camera only moves things up and down the screen.** It is oblique, the
way the field is drawn: the ground seen straight down at eight dots to the
unit, and a unit of height rising 0.75 units up the screen. Every ray is
parallel and runs up and back, so a ray only ever crosses its own column. A
metatile's window therefore shows its own cell, the strip of a *tall* south
neighbour that rises into it, and — if it is a pit — the face of the cell to
its north. Never east or west. So a cell can be rendered on its own, from a
context of at most three rows.

**A key is everything that can show.** `gen_world.land_key` gives each cell
its character and variant, which of its four sides its surface runs on
through (a road into a road, water into water — and for water, *how deep*
the water next door is, or the colour steps at the border), which sides its
mass joins (canopy, cliff, iron wall, pipe), the key of a tall south
neighbour and the key of a pit's north neighbour. That is autotiling on four
neighbours, and it is why a road has a verge, a river has banks and a forest
is one canopy instead of a grid of balls. Neighbour keys are cut down to what
shows through: a tall neighbour's north strip depends on which ways it joins
east, west and north, and not on its paving or its south edge. Before that cut
the fields came to 130 keys; after it, 109.

**Every point is lit by its own cell.** Ambient occlusion, shadows and the
pool round a lamp all come from the geometry of the cell the point is in and
nothing else, so a point on a border looks the same from both of the
metatiles it can appear in, whatever they believe about their other
neighbours. Detail that straddles a border — a grass blade, a cobble, a glint
on the river — comes from a lattice whose outer ring is seeded the same way in
every cell. The first lamp lit a square of the plaza: its pool reached past
its own cell, the next cell was not lit by it, and the border showed. Pools
fall off across the ground now and die out inside their cell.

**Seven palettes, and the land moves by palette.** A region's characters are
cut the way a backdrop's are — every character takes whichever of BG palettes
0, 1, 2 and 4-7 draws it best; 3 is the windows'. Nothing else in the field
uses 2 or 4-7, and battle, the title and the Mode 7 warp all load their own
colours there, so `ppuLoadLandPalette` puts the region's back in
`fieldLoadArea`, `ppuSetFieldMode` and when the menu closes.

Water, lamps, glowing caps, furnace mouths and rifts are rendered four times
and cut together as one picture with twelve channels, the way the title is.
What comes out is one set of characters and four palette sets, and
`ppuAnimateLand` uploads the next set every eight frames: 224 bytes of CGRAM,
against the 256 bytes of VRAM the tile animation it replaced cost — and that
could only afford eight moving characters, which is two metatiles of sea and no
banks at all. A pixel that does not move may only take a colour that does not
move either, or the ground would shimmer with the sea. It does not run while
the field menu is up, because palettes 0 and 1 are the menu's red and green
glyphs then.

The moon's glints on the water are points on that lattice, each twinkling on
its own phase. Worked out from summed ripples instead, a glint repeats every
metatile, and a river of identical diamonds is a quilt.

| region | keys | characters | moves |
|---|---|---|---|
| VILLAGE | 62 | 162 | the lamps on the square |
| FIELDS | 109 | 212 | the river |
| FOREST | 79 | 166 | the glowing caps |
| SHORE | 104 | 213 | the sea, the tide up the beach |
| SALT | 24 | 69 | nothing, which is the point of the salt flat |
| FORTRESS | 45 | 71 | the furnace mouths |
| HUSH | 20 | 40 | the rifts, the last well |

The budget is characters *after* the cut, and it goes further than the keys
suggest: half a mass does not depend on the far side of the cell, so the
quantiser finds the same characters in keys that only differ over there. No
region needs `fit_budget` to merge anything.

Two bugs worth writing down. A cliff's key starts with `#`, and `load_renders`
skips lines that start with `#` as comments: every shore cliff would have
vanished from the bake, so key lines carry a `k ` in front. And a column's
heightfield says nothing about the column beside it, so a ray marching down a
pit took one long step straight through the face of the island to its north;
the march never steps further than the column's border now.

`python3 preview.py anim` renders each moving region under each of its
palette sets, two by two, so a broken frame shows without booting anything.

---|---|---|
| VILLAGE | lantern flame | 4 |
| FIELDS | water | 4 |
| FOREST | mushroom caps | 8 |
| SHORE | water, shallows | 8 |
| FORTRESS | furnace mouths | 4 |
| HUSH | the rift | 4 |

The salt flat has nothing that moves, which is the point of the salt flat.

## The orchestra

Twenty-seven instruments cut from two CC0 libraries (`SAMPLES.md`), 19.9KB
of BRR between them. Only the instruments the score actually plays are built
into the module, so an unused recording costs no ARAM.

Three kinds, all in `orchestra.py`:

- **loop** — sustained: strings, winds, brass, organ. An attack, then a loop
  that is an exact whole number of the instrument's own periods.
- **shot** — pitched and struck or plucked: harp, marimba, tubular bell,
  pizzicato bass, timpani, the kentongan. Tuned like a loop, plays once, stops.
- **hit** — unpitched percussion, triggered at note 60.

**Tracker note 60 is middle C** (261.63 Hz) and every instrument is tuned to
it, so a note number means one pitch everywhere. The score is written in
sounding pitch, scientific naming. (The previous soundtrack had the whole
keyboard an octave off its own note names, which put every trumpet and oboe
line at 900–1800 Hz, where those instruments are at their harshest.)

### What has to happen to a recording

A ten-second 44.1 kHz stereo WAV is not a SNES instrument, and every step
below is here because doing it carelessly once produced an audible fault.

- **A real low-pass before decimation.** The first version averaged groups of
  samples, which is not a filter: everything above the new Nyquist folded back
  into the band as a fixed shimmer of inharmonic partials under every note.
  `sfsample.sample_at` is a Kaiser-windowed sinc, the same for every ratio.
  Measured on the DSP, the share of a trumpet's energy that sits on harmonics
  of the note rose from 50% (high notes) to 98%.
- **The loop is contiguous with its attack.** It used to be cut one loop-length
  *past* the attack, so the two did not meet, and four of nine instruments
  ticked once per note (a 5–7× step). The loop start is now chosen where the
  source is most periodic over the loop length and best matches the tail of the
  attack, and the head is blended into it.
- **The loop wraps into what precedes it.** smconv's BRR encoder predicts each
  block from the samples before it, and at the wrap those are the *end* of the
  loop. If the end and the attack's tail differ, the first loop block decodes
  wrong on every pass. The loop's last samples are made to equal the samples
  before its start.
- **Whole periods, on 16-sample blocks.** A loop can only re-enter at a BRR
  block boundary, so its length is a multiple of 16 — and 16 has no reason to
  divide a violin's period. Cut at a round number the loop is 11½ periods
  long, and what you hear is the loop frequency itself, a warble under a
  sustained note. The source is resampled by a fraction of a percent until *k*
  periods fit the block-aligned length, after which
  `C5Speed = 261.63 × (loop length / periods)`.
- **Samples per cycle is the timbre.** `p` samples per cycle keeps `p/2`
  harmonics, independent of pitch; 24–32 is the range used. It also fixes the
  cost: bytes scale with `p × f₀`, so a bass is nearly free and a piccolo is
  not.
- **Pitch is measured, never assumed.** `checktune.py` measures the finished
  loops (upsampled 8×) and fails the build over 18 cents; they all measure
  within a cent. It also checks the seams: no join or wrap may step more than
  the loop's own steepest ordinary step. Pitched one-shots are measured from the
  recording — by spectral peak for bars, by period for strings — and tuned to
  the *measured* pitch, because a zither string and a marimba bar are not on
  the equal-tempered grid. Both libraries name files an octave below where they
  sound, and the kentongan and the glockenspiel of the old score were
  mislabelled by 1½ octaves and one octave; the title theme's slit-drum figure
  never sounded like what was written.
- **Shape the top.** `tilt` (dB per octave above 1 kHz) and `bw` (harmonics
  kept) soften the brightest recordings before they are pitched around the
  keyboard: solo violin, trumpet, organ, oboe, the metal percussion.

**Levels.** Every sample is normalised to the same peak; `gv`, the sample's
global volume (0–64, unity at 64, so it can only turn things *down*), balances
them. `LEVELS` in `orchestra.py` was set by rendering each instrument at
tracker volume 40 through the emulated DSP and matching K-weighted loudness, so
on any sustained instrument **volume 40 is mezzo-forte and means the same
loudness**. Measured: every sustained instrument lands within ±0.2 LUFS.

Warm to harsh, same tune, same accompaniment, equal loudness, ear-weighted
share of energy in 2–6 kHz: horn (−20 dB), clarinet, flute, oboe, strings
section, viola, cello, organ, solo violin, **trumpet (−4 dB)**. That table is the
reason the score has no trumpet lead.

## Music

Fourteen original themes, written in a small score language and compiled to an
Impulse Tracker module for smconv:

| file | role |
|---|---|
| `score.py` | the notation (a line per voice, a bar at a time), the checker, the compiler |
| `orchestra.py` | the instruments and how each is cut |
| `themes_*.py` | the music |
| `gen_music.py` | assembles the modules and writes `res/music.h` |
| `sfx.py` | the eight sound effects |
| `audition.py` | plays a theme through an emulated SPC and measures it |

A theme is sections; a section is a line per voice. The compiler rejects notes
outside an instrument's range and bars of the wrong length, and reports bass
that disagrees with the written chord. Pattern data costs two bytes per *row*
(empty or not) and about four per note, so slow music is written on an
eighth-note grid, sections that repeat are compiled once, and the byte cost of
every theme is printed.

**The score is one work, not a playlist.** Three ideas recur. *The call* is
three equal notes and a leap upward — the kentongan, TUNG. TUNG. TUNG. — and it
opens the road tune. *The road* is the pilgrim's tune, bright and bugle-like:
walked in the field, bent into E minor for the fortress, and sung in full, in a
major key, in the ending. *The lullaby* is the Sleep's tune, three sighs each
falling a third: warm in the village, hollowed out in the Hush, and the thing
Il Silenzio pleads with. That boss now has two themes, one per shape: the
plea, and the same tune with its patience gone (`BGM_FINAL2`, started by
`battle.c` at the moment the second shape stands up).

### What the SPC700 driver does and does not do

Everything here was read from `sm_spc_wla.asm` or measured, and each one cost
something to learn.

- **It ignores the DSP's ADSR entirely.** Every voice runs on direct GAIN and
  the driver does its own envelope, a tick at a time. Voice volume is *only*
  pan; loudness is `sample × instrument × channel × envelope × fade`, 7 bits at
  the end.
- **A note-off needs an envelope.** `Channel_ProcessEnvelope` tests the key the
  wrong way round for an instrument *without* an envelope, so its fadeout
  starts the instant the note is struck and the note dies in a few ticks. With
  a volume envelope the driver holds at the sustain node while the key is down
  and starts the fade only after key-off. Every sustained instrument therefore
  carries a two-node envelope with a sustain node, and a fadeout (the release:
  `1020 / fadeout` ticks). The old score never used note-off at all, only a
  hard `NOTE_CUT`, and every phrase ended in a chop.
- **Tempo is clamped to 80–200.** The SPC's tick timer cannot run slower than
  about 32 ms, and the driver clamps an absolute tempo to that range. Slow
  music gets its slowness from more ticks per *row* (speed), at a tempo near
  120, which also makes a tick about 21 ms in every theme so an instrument's
  release means the same thing in all of them. `score.Theme` chooses the speed.
- **Sound effects steal voices 7 and 8**, and a sustained note on a stolen
  voice is gone for good. Nothing essential is ever written there; they carry
  ornament.
- **`spcPlay` resets the module's state** (echo enables, pans, volumes, the
  echo buffer), so per-voice echo switches cannot leak from one theme into the
  next. They *do* persist across a loop point inside a theme.
- **Position is an order number**, not a pattern number, so themes share
  patterns across their order lists and `music.h` carries order ranges.
- Vibrato, volume slides, pan, echo switches and tempo work. Tremolo,
  panbrello, tremor and fine vibrato do not.

### Not chopping the music

Two faults shipped in the first version of the new compiler, and the second
survived for hours because no loudness figure shows it.

Every sustained note was ended one *row* early. At a slow grid a row is ~17
ticks, about 350 ms, and the release is ~9 ticks, so every voice fell silent for
roughly 180 ms at every bar line. The rule now: a note ends where it ends; a
following note simply replaces it (legato); the release starts only where a
rest begins; and a note left ringing at the end of a pattern is released on the
first row of the next one unless that pattern starts a note there.
`audition.py` counts these holes (a dip to under a twelfth of the median level
inside sustained music) and fails the theme on any; it reads 0 on the score and
11 on the compiler before the fix.

Every note in a part also used to sit at exactly one volume for a whole section.
The compiler now leans on the downbeat (+3), lets off-beat subdivisions fall
away (−2) and gives long notes a step more, for the voices that carry a line.

### The mix

The echo is one set of parameters for the whole module — 48 ms, low-passed,
with the bass and the drums kept dry — and the sends are chosen per voice:
`EON` covers the tune, the harmony and the ornaments. The soundtrack sits at
about −18 LUFS with peaks around −5 dB and no clipped frame; the previous score
sat about −18 as well, but with an ear-weighted 2–6 kHz share of −7.7 dB where
this one sits near −13 dB.

The sound effects are soft, rounded sounds now (a tick, a chime, a thud, a
shimmer) stored at 8 kHz — a slit drum for the SAHUR! effect, the real
recording — played at DSP pitch 2, and quiet enough to sit in the music: they
were full-scale blips played at 13–15 of 15 on a mix peaking far lower.

### Budget

The SPC has 64 KB and smconv leaves 57,957 bytes of it for modules. The score
spends 57,460 of 57,957 bytes: 19.9KB of instruments, 26.0KB of pattern data, 6KB of
echo buffer and 5.4KB of effects, with 0.5KB free.

## Cartridge

Mode 20 (LoROM), `$FFB0`–`$FFDF` registration header per cartridge-rom.md:
`$FFD5 = $20` LoROM/SlowROM, `$FFD6 = $02` ROM+RAM+battery, `$FFD8 = $01` for
2KB of SRAM, `$FFDA = $33` — the licensee code that tells the reader to look in
the extended header at `$FFB0`. The checksum is the sum of every byte modulo
$10000 with the two checksum words counted as $00; complement and checksum must
XOR to $FFFF, which they do.

The cartridge is declared 4MB (`ROMSIZE $0C`, 128 banks) and about 349KB of it
is code and data. The rest is headroom — the declaration is what a mapper and
an emulator read, and the size is deliberate, not filled.

## Tools

Every binary the ROM embeds — tilesets, tilemaps, collision, palettes,
animation strips, H-DMA tables — is written into `assets/`. The generators name
them, the `.incbin` lines in `data.asm` and the generated `worlddata.asm`,
`bgdata.asm`, and `hdmadata.asm` read them from there, and the assembly units
themselves stay in the root because `snes_rules` globs root `*.asm` into
`OFILES`.

| file | does |
|---|---|
| `gen_assets.py` | driver: runs every generator below |
| `gen_font.py` | BG2 sheet — glyphs, icons, gauges, window frame, logo letters |
| `terrain.py` | metatile painters, shared by every region |
| `gen_world.py` | seven regions: maps, collision, events, exits, the land keys, and tilesets and tilemaps cut from the baked land |
| `gen_battle.py` | six battle backdrops: cuts the baked renders to the 256-character page, one palette per character |
| `gen_sprites.py` | resident OBJ sheet, streamed enemy blob, dialogue portraits, the sleepwalkers |
| `gen_render.py` | raymarches the pre-rendered party and every scene in `render_*.py`, and bakes them into `assets/renders.txt` (needs numpy; not run by `gen_assets.py`) |
| `render_land.py` | the land engine: the oblique camera, a cell's column, the region palette cut |
| `render_*.py` | scenes for `gen_render.py`: `sleepers`, `wilds`, `canon`, `bosses`, `portraits`, `backdrops`, `title`, `field`, `regions`; a key in `SCENES` replaces that `ENEMY_ART` or `PORTRAIT_ART` painter, a key in `BACKDROPS` that region's painted backdrop, a key in `FIELD` that kind's walking poses, a key in `LOOKS` that region's tileset |

`preview.py` shows what the *generators* produced. `capture.py` shows what the
console actually put on screen, which is the only way to observe a mistake made
between the `.pic` file and the PPU — and it is how most of the bugs above were
found. `play.py` builds on it with BFS pathfinding taken from the same
generator the ROM was built from, so a change can be checked against the whole
six-act structure rather than one screen:

```python
exec(open('play.py').read())
travel(29, 13)          # BFS across the region's own collision map
boss_fight(16, 15)      # scene, battle, and any second shape
```

`mksave.py` is the other half of that: the save block's layout is written out
longhand in `save.c` because it outlives the build, and the same property lets
Python write one. Injecting a blob into the core's SRAM and choosing CONTINUE
puts a level-24 party at the last well in about a minute, instead of the
forty-five a legitimate route takes — which is the difference between testing
the final boss once and testing it until it is right.

Two things about driving that core from Python: it wants `retro_init()` called
*before* the video/audio/input setters (its setters dereference a pointer that
`retro_init` constructs, so the documented order segfaults), and the ROM buffer
has to outlive `retro_load_game`.

## Regenerating the assets

The generated graphics and tracker modules needed for a normal build are kept
in the repository, so a contributor can build without downloading the 58MB of
source recordings. To rebuild them from their Python sources:

```sh
python3 fetch_samples.py
python3 gen_assets.py
make
```

The sprites, the backdrops, the title and the land are pre-rendered, and the
renders are checked in as `assets/renders.txt` rather than produced on every
build: they are floating point, and numpy on another machine can land one
pixel on the other side of a colour ramp. `gen_sprites.py` reads the baked
file and refuses to run if it is older than `gen_render.py`, a `render_*.py`
scene module, or the palettes, and `gen_world.py` refuses if a map changed
and now needs a metatile the bake does not have. After changing any of them
(about seven minutes, most of it the land):

```sh
python3 -m pip install numpy
python3 gen_render.py
```

Pillow is optional and only needed for previews and screenshots:

```sh
python3 -m pip install Pillow
python3 preview.py title
python3 capture.py --core /path/to/mesen-s_libretro --out shots
```

`capture.py`, `play.py`, and `perf.py` also accept the Mesen-S core through the
`MESEN_S_CORE` environment variable. `TUNGTUNG_ROM` can override the ROM path.
